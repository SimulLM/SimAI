# Router final-choice boundary, one real PD request

A real 512/64 FP16 TP1 1P1D streaming diagnostic used one warmup, the existing lightweight worker host instrumentation and the candidate router with a new `server_final_choice_observed` event. The event records the first streamed choice with a non-null `finish_reason`, before forwarding that line. It is a host observation and does not represent GPU completion or prove the client received the line. Existing `server_complete` is emitted after the backend stream and forwarding loop terminate. The router adds one synchronous event write, whose perturbation is not characterized.

The measured request was HTTP-successful, returned 512 input and 64 output tokens with `finish_reason=length`, and launcher exit code 0. On the same router CLOCK_MONOTONIC, final-choice observation occurred at 1837366352324342 ns, completion at 1837366352515623 ns: 0.191281 ms later. This is one observation, not a production distribution or independently billable tail. It excludes all work before the final output reaches the router and does not establish equivalence with simulator batch completion. The warmup is also preserved in router-events and client.json; raw worker logs remain in `/root/autodl-tmp/dag-handoff/runs/final-choice-boundary-20261126/`. Both GPUs released on shutdown.

`run.sh` and output, router source in `docs/dag_defense/environment/scripts/pd_stream_proxy.py`, and the fake-backend correlation test preserve reproduction and event semantics. This instrumentation does not mark missing terminal choices as successful coverage; existing reconciliation and failure rules remain unchanged and must explicitly check this event before claiming full boundary coverage. No formal validation was run.
