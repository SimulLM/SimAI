# Real arrival replay of batched first-token candidate

One 1024-input, eight-output requested-concurrency-4 wave from the synchronized 1P1D profiling capture supplies actual router arrival times and request mapping. The replay uses the pristine-predictor DAG worktree and the separately opt-in shared-first-token diagnostic. The fee table uses independent-within-capture per-step host interval medians for actual batch 1 and 3 (10 warmup and 30 measured waves each); it includes this selected wave and is therefore not a holdout. The interval begins after inserted KV sync and includes logits, sampling and final synchronization; do not add its subintervals. The modeled task consumes the destination GPU as an explicit, unproven approximation. Existing compute and transfer profiles and GPU exclusivity assumptions are not validated by this test.

The actual first-token groups and replayed groups were both [0] and [1,2,3], 2/2 on each side; this is membership only, not measured timing or individual actual cost equality. Audit verifies KVReady before each shared task, completion before each request's first Decode, seven Decode steps per request, successful completion and KV release. This is DAG-only, from one heavily instrumented eight-output wave; it cannot establish a natural-scheduling same-fee comparison, full cost parity, actual GPU occupancy or formal validation. Source request mapping and clocks are retained. The original request stream was nonstreaming and detailed synchronization perturbs scheduling. No validation completion time informed the candidate fee.

Run `prepare.py` and `run.py` only in a new directory with the archived referenced inputs; audit assumes the named original directory. Raw simulator commands, first-token trace, event trace, PD transfer records and process logs are in the separately hashed archive on the data disk. Formal validation remains 0/30.
