# Original predictor real-arrival calibration replay

Two existing 512/64 calibration repetitions (serial-0 and concurrency-2 concurrent-0), each 32 real requests, are replayed using actual router arrival timestamps. The original baseline is the untouched pinned `cef83f9ddd96540e3e9f48934f11335d52d54fce` checkout; DAG uses a separate worktree with the exact original predictor copied in. All four simulation processes exited 0. Existing data, original simulation and predictor-adapted comparison are preserved. This is calibration diagnosis, not frozen validation. Original predictor omits RoPE estimation and has known phase/context limitations, so common fees do not prove hardware accuracy.

Matching by replica, request IDs, token counts and prior decode histories: serial matches 1,784 of 1,853 DAG and 1,859 baseline batches; concurrency 2 matches 225 of 1,027 DAG and 1,025 baseline batches. For every one of the 2,009 matching batches, DAG summed task cost and baseline batch duration agree within 1 ns. Unmatched batches cannot be compared by this procedure. The reused audit program hard-codes the label `adapted_baseline` in paths/limitations; the baseline in this run is **pristine**, not adapted. It excludes DAG resource waiting from task cost.

First positional decode-batch divergence is saved in `first-divergence.json`: in concurrent-0, second DAG batch has request 0 while original baseline has requests 0 and 1, both at approximately 48.040 ms; in serial-0 the first divergence occurs at positional batch 102. This is an observation, not an established cause; request arrival, KV-ready events and resource order require inspection. Two cases are not a validation matrix.

Against these real calibration request completion times, MAE was 275.01 ms DAG and 269.30 ms baseline for serial-0, and 159.13 ms DAG and 153.84 ms baseline for concurrent-0. Timing boundary and operating variability remain unresolved, so these are diagnostic comparisons and cannot support a formal accuracy or DAG mechanism conclusion.
