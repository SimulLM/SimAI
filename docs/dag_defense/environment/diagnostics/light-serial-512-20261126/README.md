# Repeated serial 512/64 light host-boundary diagnostic

A real dual-H800 1P1D eager run used the fixed calibration input, five warmups and twenty serial measured streaming requests, with lightweight worker events and no explicit CUDA synchronization. All 25 returned 512/64 tokens and length finish, exit code 0; GPU memory was released. `analysis.csv` joins each router ID to the consumer backend ID and checks 64 consumer steps, KV receive host ordering, router first token, final choice and completion. `run.sh` uses the included client and records exit status. Full raw events, client responses and service logs are at the archive named in `raw-archive-sha256.txt`.

For the 20 measured requests, median [min, max] host intervals in ms: receive API 3.0429 [2.8152, 3.2428]; receive API return to first consumer step host return 7.2699 [7.2196, 7.4160]; last consumer step host return to final choice observed at router 0.7444 [0.7150, 0.7894]; final choice observed to router stream completion 0.1879 [0.1433, 0.2322]; server E2E 858.4387 [854.2535, 882.4992]. P95 values and individual absolute monotonic timestamps are in the analysis. All observations share one service session and input; they are not independent sessions or formal validation.

Host return is not GPU KVReady. The ~7.27 ms interval can include outstanding KV work and sampling, and cannot be added to the separately measured receive-through-GPU-sync cost. This run does not establish the exact overlap or identify cause. Last model-step host return can precede GPU completion, so the final-output interval is not pure router or CPU overhead. Event logging changes timing. No request E2E was used to fit fees and no parameter is frozen.
