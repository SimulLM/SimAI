# First Decode batch divergence in a 32-request calibration replay

This audit uses the concurrent-0 512/64 real router-arrival calibration replay in `dynamic-calibration-512-20261126`. It compares a readiness-corrected dynamic-first-token modified baseline with the experimental DAG; these are modeled events, not physical GPU timestamps or formal validation. Request histories are matched by membership and previous Decode counts. Event times below are each simulation's elapsed seconds from its own origin; actual router arrivals were supplied to both.

The first positional Decode difference is position 258. The preceding batch in both runs contains requests [6,7] with previous Decode counts [62,60], but completes at 5.204246 s in the dynamic baseline and 5.212105 s in the DAG. Request 8's modeled KV arrival is 5.206861 s in the baseline and 5.220597 s in the DAG. The baseline starts request 7's next single-request Decode at 5.204246 s, before request 8 is ready; it finishes at 5.221167 s, then runs request 8's first-token task and combines [7,8] in the following Decode. In the DAG, request 8's first-token task runs from 5.220597 to 5.221473 s and the next Decode begins with [7,8]. Both versions respect their own modeled KV arrival and first-token completion. `audit.json` contains exact event timestamps, IDs, hashes and the surrounding batch window.

This explains the immediate event ordering behind the first mismatch, not a single-variable root cause: prior scheduling and modeled source-transfer contention have already shifted the preceding batch and request 8's ready time. The modified baseline's slot policy and DAG resource model differ, and modeled readiness is not an exact physical KVReady. Later batch histories differ as a consequence. The complete prior comparison pairs 986/1033 baseline and 986/1027 DAG model batches with matched fees; this finding does not extend to unmatched batches or pristine first-token costs. No E2E completion value was used for tuning and formal validation remains 0/30.
