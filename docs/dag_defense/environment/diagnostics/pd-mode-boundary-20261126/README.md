# Service mode, request boundary and calibration compatibility

The original calibration used vLLM 0.8.5 V0 with `--enforce-eager`, 8 GiB KV buffer and GPU memory utilization 0.75. The server log explicitly states that async output processing cannot be used with eager mode (`calibration-eager-warning.txt`). The subsequent CUDA Graph forward profile has a different mode and must not be paired with that eager calibration as an equivalent fee dataset. This is an additional reason all prior v6/v8 replay accuracy figures are exploratory.

With CUDA Graph enabled but `--disable-async-output-proc`, 35 real 512/64 diagnostic requests each produced one consumer prefill/KV-bypass invocation and 63 Decode invocations, with no host post-step synchronization after client receipt. With the default asynchronous mode, the earlier separate run produced 64 Decode invocations with the last host sync after client receipt. Both are synchronized nonstream diagnostics, not direct GPU completion timestamps nor formal E2E. The explicit sync mode is a diagnostic candidate and has not been frozen.

A further eager-mode check matching the calibration's eager, buffer and GPU memory settings observed the same 1+63 invocation pattern for 28 requests. Exact request ID joins are in `id-join-summary.json` and `id-join-check.json`; the latter is a preliminary check, with full eager profiling tracked separately. In the pinned simulator, prefill marks one output token as processed, followed by 63 Decode iterations for output length 64. Mapping that first token to the real consumer's post-KV sampling and its CPU/GPU cost still requires a documented boundary contract.
