# Request ID and asynchronous model-step boundary diagnostic

A diagnostic vLLM 0.8.5 V0 1P1D service was instrumented to log the public `ModelInputForGPU.request_ids_to_seq_ids` field, which survives dataclass replacement. Consumer request IDs match the backend completion ID returned to the client after adding the vLLM `-0` sequence suffix. Each request's observed batched model invocations can therefore be joined by ID; this is stronger than wave-time-only association. Prefill/Decode cross-service mapping is not established by this join alone.

For 50 requests with input 512 and output 2, every consumer request had one prefill/KV-bypass invocation and two decode invocations. For 35 separate requests with input 512 and output 64, every request had one prefill/KV-bypass invocation and 64 decode invocations. For all 85 requests the final invocation started before the client received its nonstream response, while the instrumented host synchronization after that invocation returned later. In the 64-token diagnostic, the median interval between client receipt and host sync return was 6.63 ms. The CUDA event duration has no anchored host timestamp: this does not prove GPU completion happened after client receipt. Diagnostic synchronization changes timing, and these nonstream measurements are not formal E2E.

These observations show why the previous wave audit rejected post-response host synchronization events. They also mean that simply subtracting an entire decode step from simulated cost is not established: GPU occupancy, output callback and downstream scheduling must be modeled using a separately validated boundary contract. Raw events and each ID join are retained; no validation request completion times were used to tune costs.
