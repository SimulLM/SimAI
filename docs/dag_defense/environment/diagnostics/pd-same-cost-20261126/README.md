# Explicit same-fee PD comparison mode

The pinned baseline charges `(prefill_tokens + 1) * KV_bytes_per_token / bandwidth`. Previously the DAG transfer charged only `prefill_tokens * KV_bytes_per_token / bandwidth`, so nominally equal bandwidth did not produce equal per-request fees. The DAG now supports a version 1.1 configuration field `legacy_prefill_billing_extra_token`. When enabled, it uses the baseline billing basis for duration while retaining the actual valid-token KV byte count in `wire_bytes` and recording a distinct `billing_bytes` and `billing_basis` in graph metadata. Version 1.0 preserves its prior duration. The compatibility option is restricted to TP1/PP1 and zero fixed latency; outside that scope it rejects the configuration rather than claiming parity.

The pinned baseline and modified DAG were actually run on the same synthetic inputs/profiles for 8, 16 and 32 prompt tokens with identical bandwidth. Per-request transfer fees agreed to floating-point tolerance, while the DAG's `wire_bytes` retained the valid-token amount. One run used 800 Gi-bit/s as a synthetic fixture; another used the provisional 255 Gi-bit/s candidate. These are functional checks, not hardware accuracy results. Raw commands, logs, input/profile fixtures and outputs are retained in the compressed run archives; predictor caches are excluded and full directories remain on the server.

The candidate was fitted through the origin to 90 independent measured receiver-side PyNccl SimpleBuffer observations at 512/1024/2048 tokens and then rounded to the integer Gi-bit/s format used by the baseline. It is not frozen: the fitted 512-token median is about 6.8% low, and the profile excludes destination KV installation and concurrent contention. The extra billed token is an accounting convention, not a claim that the service sends an extra physical KV token. See `candidate.json`, its source hash, the KV profiling evidence, and `compatibility-20261126.json` for remaining blockers.

The focused PD suite passed 41 tests and the final full DAG suite passed 351 tests. The first full-suite invocation failed eight tests because its temporary directory was outside the repository, contrary to those tests' path requirements; the original failure is preserved, and the suite was rerun with a fresh in-repository temporary directory. The first parity run failed at 32 tokens because a synthetic predictor range stopped at 16; its log is retained and the range was corrected before subsequent passing runs. No calibration or formal validation is claimed.
