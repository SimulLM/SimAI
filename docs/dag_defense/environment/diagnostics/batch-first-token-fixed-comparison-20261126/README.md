# Fixed shared first-token diagnostic comparison

This CPU diagnostic replays synthetic two- and four-request simultaneous 512/64 traces. The baseline is the separately modified readiness-corrected baseline with an additional opt-in fixed receive-group barrier; it is not the unmodified original. The DAG is the separate pristine-predictor DAG worktree plus the experimental shared-first-token patch. Both use the same original predictor SHA-256, input trace, synthetic profile and synthetic per-group first-token fee (1.5 ms for two, 2 ms for four). The baseline barrier simply delays its selected group's enqueue and does not reserve a GPU; this is a fixed-batch dependency check with no competing Decode work, not a general baseline scheduler or physical cost model. The original unmodified baseline and its prior results remain intact.

For each case, both sides complete 1 Prefill plus 63 Decode batches: 64/64 batches match under replica, request IDs, token counts and prior Decode count, with maximum matched task-fee difference < 1 ns. Each request has 63 Decode steps; all modeled KV arrivals precede the first-token barrier and Decode begins after it. Both sides charge the shared synthetic interval once. Baseline/DAG first-token starts are 50.714/58.572 ms (two) and 88.573/112.148 ms (four), reflecting different transfer scheduling, not a measured physical link. The matching result only covers these two fixed cases and does not establish all fees or natural batches. Invalid fixed request IDs were explicitly rejected. Actual concurrent host/GPU overlap, calibrated costs, scheduler interactions and formal completion boundary remain open.

`audit.py` verifies batch keys, matched cost, first-token boundary, counts and predictor hashes from the raw data. The full raw logs, exact commands, configs, traces, negative case and the prior unmodified-original reference are preserved in the archive. No validation data informed fees; no formal validation was run.
