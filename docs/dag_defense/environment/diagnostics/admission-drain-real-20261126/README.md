# Admission fence and drain diagnostic

An opt-in ASGI middleware serializes admission and fence state in one router process. Once fenced, new completion requests receive HTTP 503; accepted requests remain counted until their ASGI handler exits, and reopening while handlers are active is rejected. `drain.py` waits for a fenced zero-active state with accepted==finished. A concurrent fake-backend test checks fencing an active request, rejection, draining, reopening and cancellation. An ASGI handler ending after cancellation does not prove its backend or connector is clean.

In a real dual-H800 1P1D diagnostic, four warmups succeeded, the middleware reported four accepted/four finished/zero active after fencing, and a subsequent request was rejected. Worker-context syncs completed before and after a four-sample 15-second window; observed queue/cache gauges and host connector buffers/data activity were zero, counters were stable, and worker PIDs mapped consistently to distinct GPU UUIDs. The conservative existing idle probe returned 2, not a readiness pass. The service stopped and both GPUs returned to 0 MiB. The real fence was applied after warmups completed; concurrent fence/drain behavior was tested with fake backends, not on a live in-flight GPU request.

This is diagnostic only, uses a single router process and observer hooks, and does not prove backend completion after client cancellation, atomic connector state, process start-time identity, or crash cleanup. It is not integrated with the formal supervisor. Existing cancellation evidence shows a producer queue can remain after an ASGI handler ends; therefore a zero active counter alone must never grant readiness. Full raw events, process maps and commands are in the hashed archive. Formal validation remains 0/30.
