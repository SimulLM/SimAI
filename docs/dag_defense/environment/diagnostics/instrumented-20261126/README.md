# Synchronous single-request PD diagnostic

A diagnostic-only monkey patch of vLLM 0.8.5 added CPU monotonic timestamps and explicit device-wide CUDA synchronization around execution, connector insertion, transfer and KV cache installation. This materially changes behavior and timings, uses `--enforce-eager`, and must not be used for the formal E2E run or as a performance cost. The original serving files were not edited; the instrumentation is supplied by `sitecustomize.py` through `PYTHONPATH`.

The client separately posted a 6-token prompt to the producer and consumer, recording the mapping from returned API request IDs; the backend adds `-0`. There was only one diagnostic request in flight. Worker events map those IDs to their actual batches. The check `verify-pd-diagnostic.py` passed: the producer GPU had completed its forward before insertion; the inserted 6-token tensors contained 1,572,864 key bytes and 1,572,864 value bytes plus 49,152 hidden-state bytes. The data pipe recorded five producer sends and corresponding consumer receives with sizes 48, 24, 1,572,864, 1,572,864, and 49,152 bytes. The consumer synchronized after installing KV and reported `bypass_model_exec=true`, then ran decode steps and returned eight output tokens with HTTP 200. Events also include startup profiling batches with numeric IDs; these are not the diagnostic request.

These timestamps bound completion after synchronization; they are not CUDA-event durations or exact GPU kernel timestamps. The first batch step starts before the connector's receive, and the first output token is sampled from received hidden states; the first subsequent `is_prompt=false` step is the first decode model step. Transport thread events lack intrinsic request IDs, so association is justified only by this isolated single-request diagnostic and matching ordered payloads; concurrent request mapping is still unverified. The events do not provide a production-safe, low-overhead complete trace or establish simulator scheduling equivalence. Decode-side NCCL log identifies SHM/direct/direct on rank 1 -> rank 0; this alone is not yet evidence of the rank 0 -> rank 1 data path. The producer's buffered NCCL channel output was lost on shutdown. The server exit code 143 reflects intentional SIGTERM after the successful client exit 0.

The archived scripts are the subsequent safer revision, accepting a new `PD_RUN_DIR` and adding NCCL per-process files. This original invocation used the same server parameters and instrumentation, with a fixed output directory and NCCL logging to the service logs. The follow-up revision must be verified separately. The raw response, events and server logs remain alongside this note.
