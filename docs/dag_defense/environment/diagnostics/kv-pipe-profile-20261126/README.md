# Independent serial PyNccl KV pipe profile

On the new two-H800 server, the vLLM 0.8.5 `SimpleBuffer` and `PyNcclPipe` transported synthetic FP16 tensors shaped like this model's actual connector payload: keys and values `[32, n, 32, 128]`, hidden `[n, 4096]`, int64 tokens and ROI. Actual GPU communication and copies were measured; the tensor contents are synthetic. The service processes were not running. The matching token IDs and ROI were checked on each iteration and representative first/last tensor values were checked. GPU0 produced, GPU1 consumed; NCCL logs show SHM/direct/direct for rank 0 to 1. Each of 512, 1024 and 2048 tokens has 10 warmups and 30 recorded measurements, plus every warmup retained in the raw per-rank CSVs. Both workers exited 0.

The rank-1 timer starts after a cross-process Gloo barrier, before `drop_select`, and ends after `torch.cuda.synchronize()`. It includes waiting for producer insertion, lookup/matching, control and data transfer, allocation and API overhead. It does not include insertion into paged KV cache or actual model execution, and this is one request at a time. Rank-0 times bound buffer insertion and device synchronization; they overlap rank-1 and must not be added. Timings are host monotonic wall time ending after device synchronization, not CUDA-event-only elapsed times. Median receiver durations are approximately 8.43, 15.77 and 31.08 ms respectively; see the raw rows and summary for full precision and spread. The p95 is nearest-rank on 30 samples.

This is independent of validation completion times, but is not a complete communication cost model: actual cache installation, batching/contention, clock boundary and mapping to the different baseline/DAG byte conventions must be resolved before freezing the same costs for both versions. The script uses fixed local ports 14789–14791 and refuses to overwrite an existing run directory. NCCL debug logging itself can perturb measurements. See source hashes and the existing vLLM environment manifest for provenance.
