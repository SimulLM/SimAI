# Decode pull interleaving correction

Reanalysed the existing instrumented 1024/2048 input, 8-output-token PD diagnostic without a new GPU run. For every receive step the audit searches the same wave for another request with both an earlier and a later Decode forward step. In 121 of 301 receive steps this proves another request's Decode was unfinished: 2/32, 30/60, 29/59 and 60/90 for 1024 concurrency 2/4 and 2048 concurrency 2/4 respectively. No such cases occurred for concurrency 1. `steps.jsonl` includes request IDs and host timestamps; this shows ordering, not simultaneous GPU execution, exact KVReady, or undisturbed behavior. This evidence is limited to the captured 8-token workload and same-wave requests.

The initial candidate deferred every receive until all preempted Decode work had completed, which contradicts these observations. The opt-in candidate now permits receiving when the worker reaches a step boundary even if an unfinished Decode request is preempted. Previously received requests in the ready queue still take priority. The precise priority, mixed-batch semantics, host and GPU costs remain unproven. Legacy push remains unchanged.

42 relevant tests passed. A two-request synthetic-arrival simulator smoke completed in both DAG and adapted baseline. The DAG audit confirms the second request's KV transfer started after the first began Decode and before it completed. The smoke uses candidate fees and is not real calibration or formal validation. Full commands, profiles, and outputs are archived at the path in `raw-archive-sha256.txt`. Independent calibration and remaining cost/semantics checks are still needed; formal validation remains 0/30.
