# GPU KV readiness interval diagnostic

Real vLLM 0.8.5 eager 1P1D FP16 TP1, 1024/2048 input and 8 output tokens, requested concurrency 1/2/4; 10 warmup and 30 measured waves per shape. 560/560 HTTP 200, token counts and backend mappings correct, consumer bypass true with seven subsequent decode steps. Both GPUs released after run. Each last cache installation API entry and a device-wide synchronization after all installation calls bound completion of *all* KV installs in that consumer batch. For an individual request the safe lower bound is its batch receive start, since earlier requests can be installed before the final call. This interval is not an exact CUDA timestamp. Sync and extensive CUDA instrumentation perturb the service; these are diagnostic data, not official E2E or a frozen fee.

For requested concurrency 1, median wait in the explicitly inserted synchronization is about 14.58 ms at 1024 input tokens and 30.56 ms at 2048; these values include outstanding asynchronous work and cannot be equated solely with network transfer. Other groups show splitting and tail effects; consult the audit, raw events and actual batch IDs. The observation directly disproves using host receive API return as KVReady and reinforces that producer buffer insert return is not transfer completion. The experiment does not itself eliminate the service/simulator pull-vs-push scheduling mismatch, nor validate overlap of costs. Formal validation remains 0/30.
