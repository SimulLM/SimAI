# Candidate validation scoring tool

`score_validation_replays.py` accepts a manifest of 30 runs and a separate frozen scoring rule, then joins each run's exported requests.csv to baseline and DAG prediction CSVs by stable request ID and input ID. Each run entry supplies `run_id`, `load`, `repeat`, `input_tokens`, `output_tokens`, `concurrency`, `requests_csv`, `baseline_csv`, and `dag_csv`. Prediction CSVs require `request_id`, `input_id`, and `predicted_e2e_s`. The rule must declare status frozen, comparison absolute_error_s and a nonnegative tie_tolerance_s; it does not choose the tolerance for the experiment. It checks the exact 1024/2048 by 1/2/4 matrix, output length 128 and five distinct repeats, and checks actual token counts.

The output retains 960 rows including unscored failures or missing predictions, reports improved/tie/degraded counts and computes absolute and relative errors. It first summarizes each repeat and reports load averages only when all five repeats are complete. It always returns acceptance status blocked: this scoring function cannot by itself prove same fees, frozen provenance, event semantics or experimental validity. Before formal use, an orchestrator must validate manifests and hashes, actual arrival replay mapping, model/cost identities and frozen rule. Synthetic tests exercise missing data, retained regressions, wrong matrix and unfrozen rule; no real validation has been scored.
