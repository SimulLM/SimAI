# Candidate validation collector: nonblocking durable writes

The candidate collector now offloads each append, flush and fsync to a worker thread under an asyncio lock. Per-request completion timestamps are captured before waiting for storage, so another coroutine can process and timestamp its response while a prior write blocks. Each wave waits for all request and durable-write operations before proceeding; storage errors propagate and no completion marker is written. Record order may differ from request order and should be joined by stable ID. Hard process termination may still leave incomplete records, which reconciliation must report, not silently repair.

A synthetic local-service fixture confirms success, failure, timeout, unsubmitted and reconciliation/preflight checks still work. A separate test injects a 0.5 second blocking write while a peer response arrives 0.08 seconds later; both timestamps remain separated by less than 0.35 seconds. Injected storage failure raises an error and prevents a completion marker. These tests do not establish production timing or service/GPU idle and are not formal validation. Initial attempt to run pytest in the vLLM environment failed because pytest is not installed; the same test was run directly in the existing vLLM Python environment without changing packages, and passed.
