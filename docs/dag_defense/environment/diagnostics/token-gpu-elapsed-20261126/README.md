# Token intervals and Decode forward events

Two independent instrumented real vLLM 0.8.5 eager 1P1D FP16 TP1 serial diagnostics, each four warmups and 16 measured requests at 512 input/64 output. All 40 requests completed; each run mapped 1008 measured post-first-token decode steps by backend request ID and ordinal. CUDA-event bounds and polling hooks add overhead and can change scheduling, and the client token interval includes router/event-loop work. This is not formal E2E or a finalized fee.

First diagnostic recorded host-polled CUDA event bounds; end-event uncertainty was too wide to isolate a GPU duration. The second used CUDA timing events on the model-forward stream and read their elapsed time after completion, without device-wide synchronization. Among its 1008 measured token gaps, 1003 were <=20 ms with median client gap 13.352 ms and corresponding CUDA forward interval median 11.872 ms. Five gaps were >20 ms, with median client gap 26.470 ms and corresponding CUDA forward interval median 23.946 ms. Five observations from one diagnostic are insufficient to explain the prior run's 458 long intervals. CUDA event elapsed time can include stream waiting or host launch gaps; it is not the sum of kernel durations or proof of root cause. Output buffering and asynchronous processing may shift ordinal association, despite per-request ordering. No conclusion that GPU or CPU alone causes the bimodal behavior is justified.

Both GPUs were released, all raw events, inputs, resource monitoring, code, audit and failed/limited result are retained. The earlier uninstrumented client diagnostic and the real profiler traces are in sibling evidence directories. No validation data were used to fit fees; formal validation remains 0/30.
