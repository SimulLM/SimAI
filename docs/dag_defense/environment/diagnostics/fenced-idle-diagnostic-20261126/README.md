# Fenced idle observation diagnostic

On actual dual-H800 1P1D, four concurrent warmup requests succeeded. A diagnostic-only file fence in the local router rejected a new request with HTTP 503; no fifth router arrival was recorded. After fencing, worker-context CUDA synchronization completed before and after four queue/cache observations spanning 15 seconds. Both worker PIDs mapped to distinct GPU UUIDs, and the mappings were unchanged in the two `nvidia-smi` process snapshots. Queue/cache gauges were zero, fresh sampled connector buffers and data-pipe activity were zero, and observed data/signal counters did not change across the window. The persistent producer signal receive is a normal-looking listener, not itself proof of an empty channel. The existing conservative probe returned 2 as designed. Service stopped and both GPUs returned to 0 MiB.

This is stronger diagnostic evidence, not formal readiness: the process-local fence is a check before request acceptance and does not atomically stop requests already in flight; snapshots are non-atomic, a stable signal listener alone is insufficient, GPU synchronization covers prior work in each worker context only, and an added observer thread/router fence changes the service. Pre-response timeout, crash cleanup, live PID start-time binding and actual formal-service orchestration remain unverified. The ordinary collector does not yet enforce this check. The fence test used a controlled local client, not a guarantee against every concurrent client. Do not use the result as proof that a later service instance is idle or as authorization to start formal validation.

`audit.py` checks the archived real records; full service logs, observations, synchronizations, router events, scripts and GPU process snapshots are in the hashed archive on the data disk. This is not a performance measurement; formal validation remains 0/30.
