# Real PD request and connector boundary diagnostic

Independent instrumented diagnostic on 2026-11-26, not formal E2E. vLLM 0.8.5 eager FP16 TP1, KV buffer 8589934592 bytes; 1024 and 2048 input tokens, 8 output tokens, requested concurrency 1, 2 and 4; each 10 warmup and 30 measured waves. All 560 requests returned HTTP 200 with expected token counts. The diagnostic router records its monotonic arrival and completion and both backend response IDs; `request-map.jsonl` joins these IDs to the producer send and consumer receive steps. The audit finds one send and one receive per request, consumer KV bypass, 7 subsequent decode steps, and the asserted host ordering for all 560. The router buffers non-streaming responses for ID recording, and CUDA events/hooks and device synchronization perturb execution; do not treat these timings as uninstrumented formal E2E.

Observed actual batch differs from client concurrency. In the 30 measured 1024-token waves requesting 4, actual producer/consumer steps consistently included batch 1 and batch 3; 2048-token waves requesting 4 included batches 1 and 2. The 4096 token batch limit and asynchronous scheduling constrain grouping. The consumer connector interval includes `select` wait and cache installation; its CUDA event also includes queue gaps. Producer interval and consumer interval can include/overlap the same transfer, so neither adding them nor assuming a constant pure wire bandwidth is justified. Deduplicated step summaries are diagnostic, and distinct steps can share waves. The 8-token diagnostic does not cover the full 128-output context distribution required by validation.
