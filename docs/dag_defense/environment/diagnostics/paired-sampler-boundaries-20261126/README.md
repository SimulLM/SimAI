# Paired sampler host and GPU boundaries

Reanalysis of the existing `pd-accounting-20261126/raw.tar.gz`, not a new GPU run or validation. `analyze.py` expects `compute-events-83657.jsonl` and `coverage-retry/requests.jsonl` extracted beside it from that archive. It checks the first measured batch-1 request has 512 input, 64 output tokens, one consumer KV-bypass step and 63 subsequent Decode steps, each with logits and sampler events. It preserves all host boundaries and paired GPU event durations in `paired-steps.csv`.

For that request, the first sampler host call took 7.173512 ms while the associated sampler CUDA event elapsed 0.246112 ms. Across 30 warmed batch-1 first steps, the sampler host call has median 7.166004 ms, p95 7.206752 ms, and range 5.738935–7.212795 ms. The 63 subsequent Decode steps in the chosen request have median sampler host call 0.427242 ms and sampler GPU event 0.297280 ms. These are paired but different measurement boundaries; a GPU event interval may contain idle gaps and cannot be summed with its enclosing or overlapping host interval. The 63 Decode steps are correlated and not 63 independent runs.

This accounting run does not synchronize immediately after KV installation, unlike `pd-postkv-512-20261126`, where the separate post-KV interval median is 0.875779 ms. The 7.166 ms host-call median is therefore not a second independent fee, nor is the contrast proof of which queued work caused waiting. Timing hooks, synchronization and file writes change execution. This evidence flags potentially substantial async waiting and strengthens the need to bound transfer/first-token overlap before freezing; it does not establish production timing, a replacement fee, or a resolution of the completion boundary.
