# Calibration replay transfer-occupancy sensitivity

CPU-only replay of the existing 32-request 512/64 concurrent-0 real calibration arrival sequence. The experimental DAG uses the same source, arrival trace, candidate first-token fees, transfer fee, and configuration as `dynamic-calibration-512-20261126` except `occupies_gpu` changed from true to false; output paths and the explanatory evidence label also differ. The comparison baseline is the readiness-corrected dynamic-first-token diagnostic, not untouched original. Both settings are model hypotheses, not established hardware bounds. The original pristine comparison remains in the preceding evidence.

With transfer GPU occupancy true, 986 of 1033 baseline and 1027 DAG batches pair; first Decode membership difference is position 258, baseline [7] versus DAG [7,8]. With it false, 265 of 1033 baseline and 1019 DAG batches pair; the first Decode difference moves to position 1, baseline [0] versus DAG [0,1]. Request 8's modeled ready time is 5.220597337 s versus 5.220636027 s, a 0.038690 ms change; its first-token completion shifts by the same amount. Matched batch fees agree within 1 ns in both settings. Each request has 63 later Decode steps and begins only after its own modeled KV readiness and first-token completion. Costs for unmatched batches and pristine first-token work are not covered by the matched-batch assertion.

Thus this single flag is not by itself an explanation for the prior position-258 mismatch; it changes earlier scheduling and batching substantially. The changed result is not an argument to select either setting because it increases or decreases matching, and no claim is made about physical transfer overlap or predictive improvement. The instrumented communication measurements do not prove exclusive or full overlap. Full command, logs and trace are preserved in the hashed server archive; `audit.py` verifies common command arguments, explicit flag difference, readiness, Decode count and pairing. Formal validation remains 0/30.
