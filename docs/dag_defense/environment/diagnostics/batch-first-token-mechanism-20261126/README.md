# Shared consumer-first-token mechanism diagnostic

This opt-in DAG-only runtime patch groups the requests selected for one simulated Decode pull. Once all KV transfers in that pull group are complete, it submits one shared consumer-first-token task with an explicit input-length/batch-size fee, then allows its requests to enter Decode only after that task completes. It rejects missing costs, mixed input lengths, non-pull mode and the old single-request first-token fee. It does not change the default simulator path or pristine baseline. Cost table values in this test are explicitly synthetic and do not represent H800 fees; the resource demand is an unvalidated modeling assumption. Batching and the initial pull are modeled, not known to match vLLM in all cases.

CPU simulation tests for two and four simultaneous 512/64 requests exited 0. Audit confirms one shared task per group (not one per request), all request KVReady times before submission, task end before each first Decode, and no KV allocations retained at completion. A separate missing batch-size-4 fee exits 1 with the expected error. First attempt failed due to an incorrect command-line module argument; all logs are retained. `audit.py`, commands, traces, configs and full timeline are in the hashed raw archive. The measured cost mapping, batch-specific concurrency semantics, fault recovery and an equivalent adapted-baseline mechanism remain unresolved; there is no same-fee E2E comparison or formal validation. No validation completion times informed this diagnostic.
