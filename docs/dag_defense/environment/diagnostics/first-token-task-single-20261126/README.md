# Single-request consumer first-token task: diagnostic only

The opt-in schema 1.5 candidate inserts a distinct consumer first-token task after KVReady and before the first subsequent Decode. It uses a measured synchronized post-KV host interval (0.000875779 s) as one indivisible task occupying the destination GPU, not as a sum of overlapping CPU and CUDA durations. The interval includes host work, GPU work and waits. A host interval modeled as GPU occupancy is an approximation; it does not describe CPU resources, noninstrumented overhead or concurrent batch semantics. The implementation explicitly rejects a second request when enabled. Default configurations retain the old behavior.

The one-request 512/64 calibration input replay completed. Audit checks exactly one first-token task, destination GPU demand, KVReady <= task start <= task end <= subsequent Decode start, 63 subsequent Decode batches and a cost delta of exactly 0.000875779 s relative to the otherwise identical candidate. This mathematical delta confirms accounting, not physical accuracy or improved prediction. The price was obtained from an independent 10-warmup/30-measured synchronized microdiagnostic, not fitted from request E2E. Both initial failed attempts and their graph schema errors are saved; the third run passed. Relevant PD tests: 50 passed. Full run directories remain in dag-handoff/runs; the selected graph, event, config, commands, status and logs are here.

The adapted baseline and pristine baseline lack this stage, so this is DAG-only sensitivity and not a same-fee comparison. The consumer first-token fee is not frozen or validated under concurrent loads. GPU sampling/CPU wait overlap, input-length/batch coverage, router boundaries and idle checks remain open. No formal validation was run.
