# Validation client first-token guard

The validation collector previously treated the first positive `usage.completion_tokens` observed as the first token, including a final-only usage count of 128. That could label final response time as TTFT and produce an invalid TPOT while still reporting success. The selected vLLM 0.8.5 router explicitly requests `include_usage` and `continuous_usage_stats`; observed real 512/64 streams in `single-stream-timeline-20261126/client.json` contain first continuous count 1, but future streams must not be assumed to do so.

The collector now records the first positive completion count and accepts a client first-token time only if that count equals 1. Missing or skipped first count fails the request and aborts the round under the existing conservative restart policy; the raw final usage and first observed count remain in the client record. This intentionally fails closed even if a server batches multiple generated tokens in its first chunk: the actual first-token time cannot be recovered from that chunk. It does not modify historical calibration data or claim exact GPU completion timing.

`test_collect_validation_run.py` exercises a synthetic local HTTP service with first count 1 followed by final 128, and a final-only response: the latter is failed with no first-token timestamp and the remaining requests in the wave/round retain their failure/not-submitted status. Success, injected failure, timeout, reconciliation, changed freeze artifact and absent freeze checks pass; see test.log. No formal service or validation run was performed. The overall arrival/completion blocker remains open because simulator last-batch completion still needs the declared server endpoint mapping and bounded residual.
