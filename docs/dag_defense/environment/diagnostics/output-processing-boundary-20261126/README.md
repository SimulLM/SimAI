# Output processing and router completion: one real request

A real FP16 TP1 1P1D 512/64 streaming diagnostic used one warmup and one measured request, with host-only events around vLLM V0 `LLMEngine._process_model_outputs` in addition to existing worker and router events. No explicit device synchronization is added by this hook; file logging and added wrappers still perturb execution. The measured request returned HTTP 200, 512 input and 64 output tokens, with 64 consumer model steps and 64 paired output-processing intervals. Both GPUs were released. Exit and raw logs are preserved.

For this request, final output processing began after the last worker model-step host return, and returned before the router observed the final choice and completed the stream. Final processing took 0.239887 ms; from its host return to router final choice took 0.588164 ms; final choice to router completion took 0.236395 ms. The median of the 64 processing calls was 0.122432 ms, but calls from one request are correlated. Worker model-step return is not GPU completion, and the remaining output interval can include IPC, serialization, forwarding and pending work. This is not a calibrated pure router fee or proof of non-overlap with candidate CPU fields.

The first attempt's request completed but produced no new output-processing events because its launcher still pointed at the old instrumentation; it is retained in the raw archive. Version 2 corrected only that launcher path and passed the event-order audit. `start-pd-output-boundary.sh`, `sitecustomize.py` and `run.sh` preserve reproduction; source and old attempts are in the hashed `/root/autodl-tmp/dag-handoff/output-processing-boundary-20261126-raw.tar.gz`. One measured request, one session; no formal validation, independent additive cost, or freeze claim.
