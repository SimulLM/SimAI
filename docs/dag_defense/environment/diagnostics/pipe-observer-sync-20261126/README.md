# Worker-context synchronization after concurrent warmup

Four real concurrent 512/8 requests succeeded. Afterwards, a nonce-based request caused each actual vLLM connector worker to call torch.cuda.synchronize on its visible device before a four-sample, 15-second host observation window. The worker PIDs match two distinct GPU UUIDs in a contemporaneous nvidia-smi process list. Fresh host buffer and data-pipe snapshots immediately before and after each synchronization were empty, idle and had unchanged counters; subsequent visible vLLM and router gauges were zero. Both workers reported successful synchronization. GPU processes exited and both cards were released after service shutdown. Raw logs, observed requests, worker acknowledgments and process list are archived.

This only synchronizes work previously submitted in each responding worker CUDA context. It does not rule out future work, other contexts, racing submissions, signal-pipe state or events missed by non-atomic snapshots. The observer's added thread and monkey patches may perturb the service. The experiment used no concurrent new requests during synchronization, did not test crash/timeout cleanup, and is not a validated formal readiness gate. Synchronization must occur before the measured E2E window. Process identity and observation checks need to be incorporated into an end-to-end run procedure before claiming formal readiness. No formal validation was run.
