# Synchronized transport and KV-install bounds for one streaming request

A separate real serial 512/64 streaming request using the same calibration input succeeded after one warmup. An opt-in hook records each PyNcclPipe GPU transport thread API start/return and then explicitly synchronizes the device; it also records cache installation calls and a post-install device synchronization. These are intrusive diagnostics, not production E2E timings. The producer's five returned data tensors are 4096, 2048, 134217728, 134217728 and 4194304 bytes (tokens, ROI, K, V and hidden), totaling 272635904 bytes; control messages, metadata and transport framing are additional. The consumer received the same sizes and made 32 cache-install calls. Background transport events do not carry request IDs; association is limited to this single-request exclusive interval.

Relative to this repeat's router arrival, the first producer tensor send API began at 38.628117 ms, the last producer send synchronization finished at 46.992371 ms, the last consumer receive synchronization finished at 47.039595 ms, and the last install API began at 48.488960 ms; post-install synchronization ended at 48.825443 ms before the router's first streamed token at 51.069751 ms. These timestamps bound operations on the host; they are not exact GPU start/end timestamps. Per-tensor synchronization alters concurrency and may serialize work, so the interval must not be substituted for unsynchronized service costs. The 0.896903151 s streaming interval is diagnostic only.

Raw service/router/client logs, CUDA synchronization events, payload records and exit code are archived; both GPUs were released. Existing lightweight unsynchronized timeline and synchronized KVReady diagnostic remain separate. This evidence narrows the sequence but does not resolve formal idle, instrumentation overhead, common CPU/GPU cost overlap or concurrency. No formal validation was run.
