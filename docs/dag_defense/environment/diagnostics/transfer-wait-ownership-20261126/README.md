# Transfer task and elapsed-wait ownership

Reanalysis of controlled-batches CPU simulations, no new measurement. The auditor verifies 2 or 4 separate sequential DAG transfer tasks, each with the original baseline's per-request 7.858456 ms transfer cost. In the simultaneous-two/four trace the original assigns all requests the same prefill-end plus 7.858456 ms ready time. The DAG schedules one 7.858456 ms task per request, so its last ready time and first decode start are respectively one/three such task durations later. Thus this modeled timing difference is transfer resource serialization, separate from early admission and with matching compute batch costs. It is not evidence that production H800 transfer uses that exact execution policy.

DAG request_metrics.csv `pd_p2p_comm_time` equals ready minus prefill end: for later requests this elapsed value includes time waiting behind earlier transfers, whereas the timeline transfer task duration is only its own work. Summing both the request-level reported elapsed time and the task duration/resource waiting would double count. Use the task timeline once to explain modeled execution, and request-level elapsed time only as an interval observation; don't treat the sum over requests as link busy time. The matching baseline reports its independent modeled cost, not physical concurrent transport. The real NCCL overlap and vLLM receive/install scopes remain unproven; model exclusivity and all-shape cost coverage are freeze gates. No validation outcome informed this analysis.
