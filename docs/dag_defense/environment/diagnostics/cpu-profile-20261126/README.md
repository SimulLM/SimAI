# vLLM host-call timing diagnostic

This separate diagnostic used the same single-GPU vLLM eager configuration as the compute profile, with request logging disabled. Instrumentation measured `Scheduler.schedule`, `ModelRunner.prepare_model_input`, `Sampler.forward`, and `LLMEngine._process_model_outputs` using the same host monotonic clock. It added no CUDA synchronization. File logging occurs outside each timed call, but the hooks and file writes perturb scheduling; schedule and prepare timing also include constructing diagnostic group metadata. The sampler host call can itself wait for GPU work or enqueue asynchronous work, so it is not a pure CPU-only measurement or a GPU-completion measurement.

The three client runs issued 1,210 synthetic profiling requests, all with two forced output tokens; none are validation requests. Each request was associated exactly once with each of the four measured operations in both prefill and decode, with no mixed batches. Nine additional unmatched events came from startup and the initial six-token smoke. `target-coverage.json` verifies all 68 target combinations (four operations over the actual batch/phase/length shapes) have at least 30 eligible observations following ten same-shape warmups. A 2048-token prefill wave of four splits into actual batches of at most two under the 4096-token cap. Raw events, client records, per-event rows, median/p95 summaries, source hashes and logs are retained.

These function boundaries are not yet proven equivalent to the simulator's Sarathi-derived `schedule`, `prepare_inputs_e2e`, `sampler_e2e`, and `process_model_outputs` definitions. Frontend routing/IPC, PyNccl transfer-side CPU work and any `ray_comm_time` equivalent are not covered. Do not add the wall-clock sampler duration blindly to GPU event intervals because it may include GPU waiting. Further compatibility checks, a shared cost mapping, and calibration remain required. Server exit 143 reflects intentional shutdown after successful clients.
