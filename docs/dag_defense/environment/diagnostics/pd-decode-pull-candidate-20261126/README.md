# Opt-in Decode-pull scheduling candidate

PD schema 1.2 adds `transfer_start_mode=decode_pull_candidate`; older configurations retain the existing push behavior. The candidate is restricted to TP1/PP1. When Decode is idle and has no previously ready or preempted requests, it selects pending migrations up to batch and prefill-token limits, reserves their destination storage, and serially submits their KV transfers. The selected Decode worker cannot start another batch during this pull; after all group members reach KVReady, they enter the Decode queue. This reflects the observed ordering and the vLLM SimpleConnector loop that calls `select` per request. It remains a candidate model, not proof of vLLM scheduler equivalence.

Unit and CLI tests: 41 passed. They cover legacy operation, opt-in schema, waiting for an occupied Decode worker, serial group transfer, KVReady gating, token budget, ready-work priority, and cleanup. A three-request synthetic-arrival simulator smoke using the same candidate fee table for DAG and adapted baseline exited 0. Its DAG audit records one group of three sequential transfers followed by Decode; see `smoke-audit.json`. These are software-mechanism checks, not measured E2E, independent calibration, or validation. Full outputs, commands and the alternative comparator are in the archive referenced by `raw-archive-sha256.txt`.

Important limitations: Decode-ready/preempted work is given priority until empty, an unverified policy that may starve new pulls; real vLLM can make different choices and may mix active Decode work with new requests. The model excludes separate host selection, KV installation, hidden-state transfer bytes, logits/sampling and router costs, and uses an unvalidated GPU-resource occupancy setting and bandwidth. The observed API ordering does not prove this candidate's numerical time or grouping matches a 128-token workload. The pristine baseline has not been modified; the adapted baseline retains its original push schedule. Identical configured fee inputs do not establish identical batching or that model and real boundaries are aligned. Independent calibration and a real trace audit remain necessary. Formal validation is 0/30; no freeze was created.

The first smoke omitted an explicit baseline communication bandwidth and is retained only as a functional check. The second smoke explicitly set 255 Gibit/s in both commands (converted by the simulator to bytes/s), used the same compute, attention, CPU, and network profile paths, and both exited 0. `smoke-v2-audit.json` verifies those arguments and the serial group ordering. This only verifies configuration equality for the smoke; it does not prove equality of each evaluated fee under different batches or validate 255 Gibit/s as the final real transport cost.
