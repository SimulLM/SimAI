# Producer and consumer first-token identity for a fixed input

For the exact first serial calibration input (SHA-256 in audit.json), two real 1P1D FP16 TP1 requests were made: one warmup and one measured. Each called the producer for one output and then the consumer for 64 outputs, greedily with seed 0 and EOS ignored. vLLM 0.8.5 was asked for logprobs with return_tokens_as_token_ids=true, so the returned identifiers come from the service's output-token IDs, not re-tokenization of text. Both calls reported 512 prompt tokens; the measured producer token and consumer first token were both token_id:29891, as were the warmup pair. The consumer returned 64 token IDs. Each producer HTTP response was fully received before the consumer request was sent; endpoint request IDs and monotonic client boundaries are in the audit.

This uses direct non-stream endpoint requests with logprobs, not the production router or normal E2E settings. It does not on its own prove actual GPU transfer or KVReady; see the separate same-input synchronized KV-bypass timeline. One input repeated twice cannot establish equality under every input, sampling policy or load. Full endpoint responses, service logs, launcher, exit and settled GPU state are in raw.tar.gz. Both GPUs were released. No formal validation or fee fitting was done.
