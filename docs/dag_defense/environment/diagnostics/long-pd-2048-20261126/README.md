# 2048-token buffer and concurrency diagnostic

The vLLM 0.8.5 SimpleBuffer default threshold is 1,000,000,000 bytes. Its `_add_to_buffer` waits while a single item plus current occupancy exceeds the threshold; an item larger than the threshold cannot enter an empty buffer. With 2048 tokens the observed tensors contain 1,073,741,824 KV bytes, 16,777,216 hidden bytes, 16,384 token bytes and 2,048 boolean ROI bytes: 1,090,537,472 bytes held in the buffer. Thus the original default cannot admit this item. This is a source-derived failure condition, not a deliberately run hang.

We set `kv_buffer_size=8589934592` bytes on both diagnostic instances, with 0.75 GPU memory utilization. In an eager, synchronized diagnostic, one 2048-token request returned HTTP 200 and KVReady. A subsequent wave of four distinct 2048-token requests posted all prefills concurrently, then all decodes concurrently: all eight backend calls returned HTTP 200; all four consumer IDs reported GPU-synchronized KVReady and bypass. The verifier passed. Actual producer batches were [2,2], and the first subsequent decode step had batch size 4. Four such source buffer items total 4,362,149,888 bytes before additional allocator overhead; the test is not a general memory-capacity guarantee.

The client pairs P and D IDs by input index. Each input is distinct, but current insertion events only contain the full batch ID list and do not independently bind an individual tensor to an ID; this is not yet a complete concurrent request/KV mapping proof. The connector transfers tokens, ROI, keys, values and hidden states; the simulation KV-only byte formula does not account for all these separately. Formal costs must use an independently measured equivalent method on both versions, including this discrepancy. All timings here are diagnostic only: synchronization and eager mode perturb them. The servers were intentionally stopped after testing, yielding exit 143. No formal validation was run.
