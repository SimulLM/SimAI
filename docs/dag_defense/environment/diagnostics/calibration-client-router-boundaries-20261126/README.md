# Calibration client and router clock boundaries

All 192 successful 512/64 calibration requests (three independent serial and three concurrency-2 repetitions) were joined by router ID and checked on same-host CLOCK_MONOTONIC timestamps. Across all requests, median client send to router arrival is 0.485 ms (p95 0.586 ms, maximum 0.818 ms), router first-token event to client first-token observation is 0.111 ms (p95 0.178 ms, maximum 0.470 ms), and router stream completion to client completion is 0.185 ms (p95 1.197 ms, maximum 98.100 ms). Per-repeat statistics and all 192 records are retained. These are client/router boundary differences, not GPU-to-router delays or a complete model of output processing.

The 98.100 ms case is concurrency-2 repeat 2, wave 0: its peer client completion occurred 0.185 ms before this request's router completion, while its own client completion occurred 98.100 ms later. The client performs synchronous JSONL writing, flush and fsync in the event-loop coroutine immediately after recording each request's completion. That could block the peer coroutine and is a plausible cause, but the original data contain no fsync start/end timestamps, so causality is not proven. Preserve the slow request; do not correct it or discard it. For future collection, client file writing should not block other request coroutines, with a separate bounded writer and durable failure handling; independently verify the effect rather than rewriting historical data.

Router server_complete denotes streaming response forwarding completion, not final GPU kernel completion. Calibration only; no formal validation and no fee fitted to these totals. The simulator request-completion boundary still needs comparison to backend output/serialization work.
