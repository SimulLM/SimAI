# Consumer first-token batch accounting

Reanalysis of independently captured, synchronized real 1P1D profiling (1024/2048 input, eight outputs). All 560 request IDs map uniquely to 402 consumer first-token model steps; every step's complete set of mapped request IDs agrees with its actual model batch. There are 118 shared first-token steps, including 90 measured after warmup. A step-level inclusive host interval covers post-KV-sync logits, sampling and final sync once for the whole batch. A per-request charge of the entire same interval would duplicate shared work; CPU and GPU subintervals cannot be added on top. This does not say that request latency excludes shared work or that an inclusive host interval consumes the GPU exclusively.

For the 30 measured 1024-input requested-concurrency-4 waves, 30 actual batch-3 steps include 90 requests. Their summed measured host interval is 22.510 ms; multiplying each complete shared interval by three would produce 67.531 ms, an extra 45.021 ms of work-accounting in this instrumented sample. These are work sums across waves, not production latency savings or per-request E2E corrections. Similar row-level counts and sums are in `summary.csv`; all 402 distinct step IDs, member IDs and intervals are in `distinct-steps.jsonl`. Data contain synchronization and only eight outputs, share a session, and cannot determine production overlap.

This finding rules out lifting the existing single-request consumer-first-token fee into a per-request concurrent task. A concurrency-capable comparison must identify the real/modelled receive batch and charge its corresponding first-token operation once, enforce all KV dependencies, and apply a comparable fee mechanism to the separately labelled adapted baseline and DAG. The pristine baseline remains separate. Existing first-token code still rejects multiple requests; this analysis does not claim it is fixed, and no costs were frozen. Formal validation remains 0/30. Source archive path and hash are in `audit.json`.
