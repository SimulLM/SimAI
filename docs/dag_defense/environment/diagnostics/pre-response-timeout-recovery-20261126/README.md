# Pre-response cancellation and restart recovery diagnostic

In an independently started dual-H800 1P1D diagnostic service, four warmups succeeded. A fifth client deliberately cancelled after its router arrival was recorded but before receiving response headers; this is a controlled disconnect, not an exhaustive deadline-timeout or crash test. The router continued to await Prefill: it recorded a successful Prefill response about 86.6 ms after client cancellation, then submitted Decode and logged `CancelledError`. During the following four samples across 15 seconds, the producer connector observer reported one queued item throughout while the consumer had zero. Producer insert count was five and consumer select count four; this is consistent with an unmatched residual, but sampled host state alone does not identify its contents or prove every GPU operation. The router reported an unresolved error, so the existing conservative probe returned 1. A zero GPU utilization or zero engine cache gauge would not justify reuse of this instance.

The diagnostic launcher was stopped, both GPUs returned to 0 MiB, and a new service instance was started. Its four warmups succeeded; a fenced 15-second observation recorded zero host connector queues and data activity, stable counters, two worker-context CUDA synchronizations, and stable distinct PID/GPU UUID mappings. The restart observation's conservative probe returned 2, not a formal readiness pass; it is not proof of recovery for other timeout stages, crash behavior or a later instance. Treat any timeout, cancellation or failure as invalidating that run and restart the service before a subsequent run, preserving the failure and checking fresh service state. This is an operational candidate policy until integrated and validated in the formal runner.

`audit-timeout.py` and `audit-recovery.py` verify preserved records. Raw logs, events, observer files, sync records and GPU process maps are in the hashed archive on the data disk. The router/observer patches affect service behavior, and neither this diagnostic nor its recovery is a formal E2E or validation run. Formal validation remains 0/30.
