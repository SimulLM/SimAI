# DAG 改造答辩实测清单与交接计划

编制日期为 2026-11-25。本任务面向接手实测的同学，成果用于结项答辩中的原 SimAI 与 DAG 版预测对照。

## 1. 本次要交付什么

核心任务是在一个明确配置上采集真实推理数据，使后续分析者可以用同一批请求分别运行原 SimAI 和同费用 DAG，比较逐请求耗时误差。优先测单机双 H800 的 PD 场景。

最终比较列为实测、原版预测、同费用 DAG 预测；如需改动费用，修订费用 DAG 另列。判断 DAG 时序机制的贡献时，原版与同费用 DAG 使用相同计算及通信费用。

实测成功表示采集到完整、可重放的数据。精度是否改善由后续验证决定，持平和退化记录全部保留。此次任务只签署实际覆盖的模型、硬件、负载与服务配置结论。

独立 CPU 机制实验、PD 争用图与 MoE 热点图由本地仿真负责人另行准备。GPU 实测的必做部分为下述 PD 测量；MoE 实测是条件具备后追加的任务。

## 2. 开机前检查与配置冻结

### 2.1 建议设备

| 项目 | 本轮默认选择与记录要求 |
|---|---|
| GPU | 同一服务器上的 2 张独占 H800 80 GB，两个服务进程分别只使用一张卡 |
| 互联 | 优先具有 NVLink 的卡对；用实际拓扑和传输后端日志确认使用路径 |
| CPU 与内存 | 建议至少 16 个可用逻辑核、128 GB 主存，记录实际配额和进程绑定 |
| 磁盘 | 建议至少 100 GB 可用空间，保存模型、环境、日志和原始 trace |
| 系统 | Linux；保存发行版、内核、驱动、CUDA、PyTorch、NCCL、服务框架完整版本 |
| 模型 | 默认 Llama-2-7B、FP16、TP1；记录真实模型来源、权重版本及文件哈希 |
| 部署 | 1P1D，一卡 Prefill，一卡 Decode；固定 KV 传输后端和服务调度参数 |

模型访问权限应提前取得。采用其他模型或 BF16 时，在冻结文件中记录并重新通过下述兼容性检查。

## 3. 时间与请求记录规范

所有数值字段带单位。正式数据统一使用秒，原始单位和换算依据另存。所有缺失字段留空，并在 `missing-fields.json` 中提供原因。

### 3.1 每条请求必须记录

`requests.csv` 每行一个请求，至少包含以下字段。

| 字段 | 含义 |
|---|---|
| run_id、request_id、input_id | 运行、请求、输入的稳定标识；请求通过服务端和各阶段时保留映射 |
| scheduled_arrival_s | 负载脚本预定发送时刻，相对本轮起点 |
| client_send_s、client_first_token_s、client_complete_s | 同一客户端单调时钟记录发送、接收首 token、收齐响应 |
| server_arrival_s、server_complete_s | 服务入口接收请求和服务完成的时刻；统一时钟原点并明确事件定义 |
| actual_input_tokens、actual_output_tokens | 实际送入模型的输入与实际生成长度，按服务器分词结果核验 |
| status、error | success、failed 或 timeout 及错误详情 |

主指标选 `server_complete_s - server_arrival_s`，对应服务内等待与执行。仿真回放使用实际 `server_arrival_s`，同时保留客户端实到与预定到达以解释负载偏差。

另报告客户端 E2E、TTFT 和平均 TPOT。客户端平均 TPOT 在输出数大于 1 时定义为 `(client_complete_s - client_first_token_s) / (actual_output_tokens - 1)`；说明 complete 是否包含结束标记接收开销。保留逐 token 接收时刻可进一步核查。

只有客户端日志时，可先保留原件，但需要证明仿真边界能够覆盖客户端网络、代理与响应开销，或补采服务端时间后才进入本轮主指标对照。

### 3.2 用于解释 DAG 等待的事件

`events.csv` 至少保存 request_id、event、timestamp_s、process、device、clock_id。事件包括 Prefill 开始/结束、KV 可发送、传输开始/结束、目标 KVReady、首轮 Decode 开始、请求完成。若批次共享事件，保存 batch_id 与 request_id 的映射。

记录 KV payload 字节、源/目标 GPU、传输后端、实际分块和传输路径。请求等待原因应来自排队或资源日志，可推导项附推导规则。CPU API 返回、CUDA 提交、GPU 完成分别命名。

跨进程统一为本机同一单调时钟原点，保存换算方法。GPU profiler 相对时间与服务日志对齐需记录锚点和误差。GPU 耗时采用 CUDA event 或 profiler 完成事件测量；正式 E2E 热路径中的额外同步会改变负载，详细诊断单独运行。

## 4. 采集顺序和实验矩阵

### A. 环境与冒烟

保存 `nvidia-smi -q`、`nvidia-smi topo -m`、GPU UUID、PCI 地址、MIG 状态、功耗和时钟设置、CPU/内存配额、磁盘、系统与依赖清单。记录同机其他 GPU 是否有租户、卡间链路是否共享，以及可见的后台负载。

验证一条请求通过 Prefill、KV 传输、Decode 正常完成，核对输入输出长度、request_id 贯通和时钟顺序。保存真实启动 argv、环境变量白名单、标准输出、错误输出和退出码；证据中清除访问令牌。

### B. 独立费用采集和 calibration

先采可导入两版预测器的计算画像和 KV 传输测量。计算覆盖验证所需的输入长度、Decode 上下文长度、实际 batch 范围及所需分项；需要插值时冻结方法并说明覆盖范围。传输测量包括实际 KV 布局、dtype、payload 与单次耗时，保存每次测量值而非仅均值。

每个费用点先预热 10 次，再至少测 30 次，记录同步方法和统计量。费用采集产生的硬件微基准可覆盖验证形状；整条验证请求的完成时间不得反向用于设定费用。

请求级 calibration 采用输入 512 tokens、输出 64 tokens，分别运行串行和并发 2 两档，每档 32 请求、3 次独立重复。每次重复从无积压、KV 已清理的状态开始。仅用此组诊断和修正实现、时钟或费用问题。

完成后写入 `parameter-freeze.json`，固定费用文件及哈希、两版源码快照、服务配置、验证输入和评分规则，再执行 validation。

### C. 冻结 validation

| 输入长度 / 输出长度 | 负载档 | 每次请求数 | 独立重复 |
|---|---|---:|---:|
| 1024 / 128 tokens | 串行，无重叠 | 32 | 5 |
| 1024 / 128 tokens | 每波同时发送 2 条，波间等待全部完成 | 32 | 5 |
| 1024 / 128 tokens | 每波同时发送 4 条，波间等待全部完成 | 32 | 5 |
| 2048 / 128 tokens | 上述三档各执行一次 | 每档 32 | 每档 5 |

正式矩阵共 30 个运行、960 条请求。使用固定 seed 的 token 输入，输入文件按 calibration/validation 分开保存。不同请求使用独立内容，保留实际 token IDs 或可逐字重放的原文、tokenizer 版本和哈希。传输字节由模型和实际输入确定。

预热请求放在正式测量窗口之前且明确排除；预热结束等待服务空闲。正式请求从发出到全部完成全程保留，包含失败和超时。validation 顺序在冻结时用固定 seed 打乱，每轮记录空闲状态与资源占用。

先用轻量服务事件日志完成正式 E2E 测量，再对每档选定的固定波次做独立 profiler 诊断。保存两套运行标记；详细 profiler 的性能扰动单独报告。

看过验证结果后若继续修正，保留这一批结果并标记已用于诊断，重新建立新的独立验证批次。

### D. 条件具备后补 MoE

若团队另有能在所租硬件运行、且两版支持的 MoE 模型，另立冻结配置。记录逐层逐轮专家路由、token 到专家的计数、top-k、专家放置、dispatch/combine 字节及专家结束、join、请求完成时刻。均衡和热点对照固定 token 总数与单位费用，并核验每张卡工作量和传输变化。

Llama-2-7B 的 PD 实验覆盖 dense 模型的 PD 场景。此任务完成后，可在答辩中据此签署该配置的结论。MoE 数据另行签署其实际覆盖范围。

## 6. 产物目录与验收状态

本次为答辩专项，统一采用 `dag_defense`。本清单位于 `docs/dag_defense/hardware-measurement-plan.md`。

- 服务器原始目录采用 `<data_root>/dag_defense/<run_id>/hardware/`，data_root 在 README 中填写绝对路径。
- 回传本机后保存为 `results/dag_defense/<run_id>/hardware/`；run_id 采用 `YYYYMMDD-defense-h800-pd-NN`，新批次使用新编号，拒绝覆盖。
- 仿真、对账、评分和图表的运行文件保存在该 run_id 的其他子目录；冻结配置位于 `configs/dag_defense/`，后续工具位于 `scripts/dag_defense/`。
- 可拉取的答辩总入口、验收报告、PPT 用 PNG/SVG 与作图 CSV 分别放在 `docs/dag_defense/README.md`、`acceptance-report.json` 和 `figures/`；正式证据包与校验和放在 `docs/dag_defense/artifacts/`。这些是后续交付路径，本次仅生成实测任务文档。

实测人员先按以下项目自检再交付。

- [ ] calibration 与 validation 分组及冻结顺序清楚。
