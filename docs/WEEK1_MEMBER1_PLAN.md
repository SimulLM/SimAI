# 第一周执行计划（成员一：项目负责人、架构与验收）

## 1. 本周目标

本周只完成基线固化、架构梳理、接口设计、验收与结果汇总，不开发新业务功能，不修改核心算法。

最终目标是让四位成员在统一 Linux 环境、同一仓库提交、同一子模块版本和同一输入下，获得可比较、可追溯的 SimAI/Vidur 基线结果；同时明确请求、计算、通信、网络和调度各层当前已具备的能力、接口边界与尚未闭环的链路。

成员一对本周整体结果负责，重点完成以下工作：

1. 固化仓库、分支、Issue、PR 和实验归档规则。
2. 固化统一输入、命令、环境记录格式和验收标准。
3. 审核 AICB、Astra-Sim、SimCCL、ns-3、Vidur 之间的数据边界。
4. 形成请求级指标、计算事件、通信 flow、网络结果之间的数据流说明。
5. 汇总四位成员的复现证据，主持每日同步和周末复盘。
6. 在第二周开始前提交 EP AllToAll 请求、通信结果和请求级回写 schema 初稿。
7. 建立初版精度评估框架，明确后续如何比较仿真值与真实或可信基线。

## 2. 范围边界

### 本周范围内

- 只读检查代码、配置、测试和既有文档。
- 在统一 Linux 环境中执行仓库自带基线。
- 记录版本、输入哈希、命令、输出位置、结果和错误。
- 审核并汇总其他成员提交的实验记录和模块说明。
- 编写或修订计划、实验记录、架构、接口和验收类文档。
- 对发现的问题创建 Issue；确需修复时另开最小化 PR，不与本周计划文档混合。

### 本周范围外

- 不实现动态 MoE、EP AllToAll、PD KV 传输或请求—网络闭环。
- 不修改 SimCCL、Astra-Sim、ns-3、Vidur 的核心算法。
- 不以 DeepSeek trace 宣称 TTFT、TPOT、P95/P99 或吞吐的端到端精度。
- 不租用 GPU 或多节点 RDMA 资源。
- 不把生成的二进制、`results/`、私有画像、Token 或 `.env` 提交到仓库。

## 3. 固定基线与统一口径

| 项目 | 固定值或要求 | 验收证据 |
|---|---|---|
| 主通信输入 | `example/workload_analytical.txt` | 文件 SHA-256、运行命令、结果目录 |
| 网络参数 | `example/busbw.yaml` | 文件 SHA-256 |
| 最小通信冒烟 | `example/microAllReduce.txt` | 命令、退出码、关键输出 |
| PD 调度基线 | `vidur-alibabacloud/tests/test_pd_separation.py` | pytest 命令、通过/失败数、日志 |
| 仓库版本 | 同一顶层 Git SHA | `git rev-parse HEAD` 输出 |
| 子模块版本 | 三个子模块使用同一固定 SHA | `git submodule status --recursive` 输出 |
| 环境 | Linux；记录发行版、内核、CPU、内存、GCC/G++、CMake、Python、pytest | 原始命令输出 |
| 随机性 | 有随机种子的场景必须显式记录 | 种子和配置快照 |
| 失败记录 | 不允许只写“跑不起来” | 完整错误、退出码、复现步骤、已排查项 |

统一主基线命令：

```bash
git submodule update --init --recursive
./scripts/build.sh -c analytical
./bin/SimAI_analytical -w ./example/workload_analytical.txt \
  -g 9216 -nv 360 -nic 48.5 -n_p_s 8 -g_p_s 8 -r example-
```

统一 Vidur 基线命令：

```bash
cd vidur-alibabacloud
pytest tests/test_pd_separation.py
```

所有成员必须保留原始日志；汇总表只摘录结论，不替代原始证据。

## 4. 每日执行安排

### Day 1：冻结基线与建立验收机制

目标：所有成员在开始实验前使用同一口径。

- 记录并发布顶层仓库 SHA、三个子模块 SHA、当前集成分支和基线日期。
- 计算三个固定输入文件的 SHA-256。
- 发布统一实验记录模板、文件命名规则和结果目录规则。
- 建立第一周验收矩阵，为每项交付指定负责人、审核人、截止时间和证据链接。
- 明确分支、Issue、PR、代码评审和生成物排除规则。
- 召开 15 分钟启动同步，确认四位成员环境、依赖和阻塞。

当日退出条件：四位成员确认版本和输入一致；每位成员都已建立自己的实验记录；所有验收项均有负责人和证据栏。

### Day 2：负责人独立复现与数据边界初审

目标：成员一独立走通统一流程，确保自己能审核他人的结果。

- 在统一 Linux CPU 环境中执行依赖检查、解析模式构建、最小通信冒烟、主通信基线和 Vidur PD 测试。
- 对每步记录开始/结束时间、命令、退出码、输入哈希、输出路径和关键日志。
- 将失败按“环境、依赖、构建、输入、运行时、测试断言”分类；仅记录和建 Issue，不私自改核心逻辑。
- 只读核对现有架构说明与实际入口，初步确认各模块生产/消费的数据。
- 审核成员二和成员三的基线记录是否满足可复现要求。

当日退出条件：成员一有一份完整基线记录；每个失败都有复现步骤和归属；不存在只有截图或口头结论而无命令与日志的结果。

### Day 3：系统分层、指标来源与闭环边界

目标：形成一份可被全组共同评审的数据流说明。

- 按以下主链路逐段记录输入、输出、格式、调用入口和当前限制：

```text
请求到达与调度
  -> Prefill / Decode / MoE 事件
  -> TP / PP / EP 通信请求
  -> Astra-Sim / SimCCL flow
  -> 解析模型或 ns-3 网络结果
  -> 通信时延回写请求级模拟
  -> TTFT / TPOT / 吞吐 / 尾时延
```

- 审核成员二的通信调用链和 AllToAll/`ALLTOALL_EP` 支持边界。
- 审核成员三的 Vidur 执行链、PD 配置、指标产生位置和 KV 传输缺口。
- 审核成员四的工作负载字段说明和 DeepSeek Prefill/Decode 关键事件表。
- 建立“已实现、部分实现、未实现、待验证”四态能力矩阵，禁止把目标架构写成现有能力。
- 明确 DeepSeek trace 仅用于事件顺序、占比和重叠关系的行为校准，不作为端到端服务真值。

当日退出条件：每条跨模块箭头都有生产者、消费者、数据格式和证据路径；请求—通信—网络—指标未闭环之处被明确标记。

### Day 4：接口 schema 与精度评估框架初稿

目标：为第二周实现准备可评审、可版本化的接口草案，不写实现代码。

- 编写 `EP AllToAll 请求 schema v0`，至少包含：schema 版本、请求/批次/阶段标识、dispatch 或 combine、源/目的 rank、EP 组、字节矩阵、dtype、拓扑标识、时间/依赖信息和随机种子。
- 编写 `通信结果 schema v0`，至少包含：请求标识、后端类型、总通信时延、排队/传输分解、开始/结束时间、状态、输入哈希、拓扑哈希、仿真器版本和缓存键。
- 编写 `请求级回写 schema v0`，说明通信结果如何进入 Prefill/Decode 关键路径，以及如何影响 TTFT、TPOT、完成时延和尾时延聚合。
- 写明单位、必填/可选字段、兼容策略、失败语义和缓存确定性要求。
- 建立精度评估指标清单与公式：绝对误差、相对误差、P95/P99 误差、吞吐误差、通信时延误差、事件持续时间占比误差、计算—通信重叠误差及仿真运行成本。
- 组织一次跨模块接口评审，只冻结语义和边界，不冻结未经验证的实现细节。

当日退出条件：三个 schema 能用一个固定 EP 矩阵示例串联；所有时间和字节字段都有单位；所有指标都定义参考值来源和不可比较条件。

### Day 5：全组验收、差异分析与周末复盘

目标：形成可审计的第一周结论，并为第二周提供清晰入口。

- 收齐四位成员的环境记录、原始日志和一页说明。
- 按验收表逐项标记通过、失败、阻塞或证据不足，不以“在某台机器上跑过”代替验收。
- 对比环境差异、版本差异、输入哈希、命令和输出，解释不一致结果。
- 汇总当前可验证能力、尚未闭环能力、已知限制和风险优先级。
- 主持周末复盘：每人说明完成项、证据、阻塞和下一周接口依赖。
- 给出第二周入口条件：仅当固定 EP 矩阵、输入输出 schema、预期结果和测试范围评审通过后，才开始端到端闭环实现。

当日退出条件：周总结中的每个结论都可追溯到记录或代码证据；失败项有负责人和下一步；第二周不存在未定义接口便开始编码的任务。

## 8. 精度评估指标初稿

| 层级 | 指标 | 初步定义 | 第一周状态 |
|---|---|---|---|
| 请求级 | TTFT 误差 | `|sim - ref|` 和 `|sim - ref| / ref` | 只确认输出能力，不做真实精度结论 |
| 请求级 | TPOT 误差 | 单请求及聚合绝对/相对误差 | 同上 |
| 请求级 | P95/P99 时延误差 | 仿真分位数与同口径参考分位数之差 | 缺少端到端真值时不得计算 |
| 请求级 | 吞吐误差 | 同请求分布和时间窗下的相对误差 | 缺少端到端真值时不得计算 |
| 通信级 | 通信时延误差 | 集合通信总时延及阶段分解误差 | 后续用可信通信基线校准 |
| 行为级 | 事件持续时间占比误差 | 事件时长/trace 总时长的占比差 | 可用 DeepSeek trace 做行为比较 |
| 行为级 | 计算—通信重叠误差 | 重叠时长或重叠比例之差 | 可用 DeepSeek trace 做行为比较 |
| 成本 | 仿真运行成本 | wall time、峰值内存、生成数据量 | 所有后续实验必须同时报告 |

若参考值为零、采样口径不同、硬件/拓扑元数据缺失或事件无法对齐，应标记为“不可比较”，不能强行给出相对误差。

## 9. 协作与汇报节奏

- 每日一次 15 分钟同步，每人只汇报：昨日完成、今日计划、当前阻塞。
- 每日结束前更新验收表和证据链接；聊天记录不能替代文档或日志。
- 成员一当天审阅新增结果，次日上午前反馈证据缺口。
- 跨模块接口问题先写设计 Issue，再进入实现；接口变更至少由受影响模块负责人共同评审。
- 一个 PR 只解决一个问题；本周发现的实现缺陷默认记录，不顺手重构。

## 10. 风险与预案

| 风险 | 触发信号 | 本周处理方式 |
|---|---|---|
| 当前工作站不是统一 Linux 环境 | Bash 构建脚本或依赖无法执行 | 将 Windows 检查仅作为预检；正式验收转到约定 Linux 环境 |
| 子模块状态无法可靠读取 | Git 工具链或 PATH 异常 | 记录原始错误；修复环境后重新采集，不猜测 SHA |
| 四人结果不一致 | SHA、哈希、命令或环境有差异 | 先对齐输入和环境，再比较结果 |
| 主基线耗时或失败 | 构建/运行退出非零 | 保留完整日志，最小化复现并建 Issue，不修改核心逻辑掩盖问题 |
| DeepSeek trace 过大或元数据不足 | 无法直接加载或事件含义不清 | 先做流式元数据扫描和抽样核对，明确不可解释字段 |
| 把目标能力误写成现有能力 | 文档无代码/运行证据 | 使用四态能力矩阵并要求证据路径 |
| 接口设计过早绑定实现 | schema 出现后端私有字段 | 保持请求、结果、回写分层，后端差异放到扩展字段 |
| 误用 trace 得出端到端结论 | 报告出现 TTFT/TPOT 真值表述 | 阻止验收并改为行为校准结论 |

## 11. 完成定义

本周仅在以下条件全部满足时视为完成：

- 四位成员均提交环境与复现记录，版本、输入、命令、结果和错误可追溯。
- 主通信基线生成结果，Vidur PD 测试通过；若有失败，已形成可复现问题记录并明确负责人。
- DeepSeek Prefill/Decode 关键事件表完成，且明确其可校准与不可校准范围。
- 请求、计算、通信、网络、调度五层现有能力及边界已形成证据化说明。
- 请求—通信—网络—指标闭环的缺口被明确描述。
- EP AllToAll 请求、通信结果和请求级回写 schema v0 通过跨模块评审。
- 初版精度评估指标清单包含 TTFT、TPOT、P95/P99、吞吐、通信时延误差和运行成本，并说明参考数据要求。
- 周末总结完成，每个结论均能回溯到代码、配置、日志或实验记录。
