# SimInfer 第一周

## 一、项目研究主线与第一周统一验收目标

### 1. 项目研究主线

SimInfer 的研究主线是：

> 构建面向大模型推理的高精度、可扩展、可校准的端到端仿真系统。

这里的“高精度”不能停留在口号层面，而必须拆解为可验证的系统能力：

- **请求级精度**：能够预测 TTFT、TPOT、P95/P99 时延、吞吐等请求级指标。
- **计算级精度**：能够反映 Prefill、Decode、批处理策略以及不同并行策略之间的性能差异。
- **通信级精度**：能够描述 TP、PP、EP 等集合通信，尤其是 MoE 场景中的 AllToAll 通信及其引发的网络拥塞。
- **网络级精度**：关键场景使用 ns-3 获得分组级网络结果，而不是仅依赖简单带宽公式。
- **调度级精度**：能够表达 PD 分离、KV 传输、资源竞争以及请求到达过程。
- **校准精度**：使用真实或可信的 profile、实验数据和基线结果，量化仿真结果与真实系统之间的误差，而不是主观地描述“很准”。

因此，项目的核心科研问题应表述为：

> 如何构建一个同时覆盖请求调度、计算执行、集合通信与网络竞争的 LLM 推理仿真系统，并在可接受成本下获得可校准的高精度预测？

后续的 MoE、PD、AllToAll 和 ns-3 网络仿真不是彼此独立的功能模块，而是验证系统“高精度”能力所必需的关键场景。整体链路应逐步形成：

```text
请求到达与调度
      ↓
Prefill / Decode / MoE 算子与依赖
      ↓
TP / PP / EP 通信请求
      ↓
SimCCL / Astra-Sim 生成通信 flow
      ↓
解析模型或 ns-3 网络仿真
      ↓
通信时延回写请求级模拟
      ↓
TTFT、TPOT、吞吐、尾时延与误差评估
```

后续每新增一项能力，都必须回答两个问题：

1. 它让系统多模拟了哪个真实现象？
2. 它让预测误差下降了多少，或者在哪些场景下使预测结果更可信？

最终成果不应表述为“我们增加了 MoE 模块”，而应表述为：

> 我们构建并验证了一个面向 MoE 与 PD 场景的高精度 LLM 推理仿真框架，能够在请求、算子、通信与网络多个层次联动预测性能，并量化其精度、成本和适用边界。

### 2. 第一周统一验收目标

本周不开发新业务功能，不修改核心算法。

本周唯一目标是：四位成员在统一的 Linux 环境、相同提交版本、相同子模块版本和相同输入下，完成同一套 SimAI/Vidur 基线，并得到可比较、可追溯的结果。

第一周的基线工作不是简单的环境配置，而是对系统各层可复现性的初步验证。后续每一项新增能力，都应在此基础上进行增量验证，并比较其对预测误差、适用场景和仿真成本的影响。

统一验收基线包：

| 用途      | 固定输入                                             | 说明                                                                |
| ------- | ------------------------------------------------ | ----------------------------------------------------------------- |
| 主通信基线   | `example/workload_analytical.txt`                | 包含 AllReduce、AllGather、ReduceScatter、AllToAll、`ALLTOALL_EP` 等通信语义 |
| 网络参数    | `example/busbw.yaml`                             | 解析通信模式使用的带宽配置                                                     |
| 最小通信冒烟  | `example/microAllReduce.txt`                     | 快速确认基础集合通信路径                                                      |
| PD 调度基线 | `vidur-alibabacloud/tests/test_pd_separation.py` | 验证 Vidur 的 Prefill/Decode 分离配置和集群行为                               |

主基线运行命令：

```bash
git submodule update --init --recursive
./scripts/build.sh -c analytical
./bin/SimAI_analytical -w ./example/workload_analytical.txt \
  -g 9216 -nv 360 -nic 48.5 -n_p_s 8 -g_p_s 8 -r example-
```

Vidur 基线测试命令：

```bash
cd vidur-alibabacloud
pytest tests/test_pd_separation.py
```

本周验收标准：

- 每位成员提交一份环境与复现记录。
- 记录操作系统、编译器、Python、Git SHA、三个子模块 SHA。
- 记录实际运行命令、输入文件校验值、关键输出位置和运行结果。
- 主通信基线能够生成结果；Vidur PD 测试通过。
- 完成 DeepSeek `prefill.json` 与 `decode.json` 的解析，提交关键事件表：事件类别、开始时间、持续时间、并行/等待关系、EP 配置与数据来源。
- 明确记录当前能够输出的请求级、计算级、通信级和网络级指标。
- 对当前尚未闭环的链路进行边界说明，尤其是通信时延如何反馈到请求级指标。
- 任何失败都必须记录错误信息和复现步骤，不允许只口头描述“跑不起来”。

注意：`workload_analytical.txt` 只是第一周的固定、可控系统基线，不是最终科研实验数据集。第二阶段再引入可控的 MoE 偏斜矩阵、真实或可信 profile，以及用于校准的实验数据。

第一阶段的公开校准参考确定为 DeepSeek 的 [profile-data](https://github.com/deepseek-ai/profile-data)。该数据提供 V3/R1 训练、Prefill 和 Decode 的 PyTorch Profiler trace，可用于比较计算、AllToAll 与等待事件的顺序、持续时间占比和计算—通信重叠比例。它采用均衡 MoE 路由，并不是端到端服务压测数据，因此不能直接作为 TTFT、TPOT、P95/P99、吞吐或偏斜 MoE 场景的绝对真值。

DeepSeek trace 的解析是第一周的优先任务，不是后续开发完成后的工作。第一周先形成 Prefill/Decode 的关键事件表；第二周的 EP AllToAll 接口设计和实现以该事件表为参考；在请求—通信—网络闭环实现后，才对仿真输出和 trace 做系统化对齐与误差分析。

## 三、必读

我们不是从零开始做一个推理系统，而是基于 SimAI、AICB、SimCCL、Astra-Sim、ns-3 和 Vidur，建立一个面向大模型推理的高精度、可扩展、可校准的端到端仿真系统。

这里需要先明确，“高精度”不是一句宣传语，而是必须通过可验证的能力来定义。我们至少需要从六个层次进行验证。

第一是请求级精度，系统要能够预测 TTFT、TPOT、P95/P99 时延和吞吐。第二是计算级精度，要能够反映 Prefill、Decode、批处理以及不同并行策略的差异。第三是通信级精度，要能够描述 TP、PP、EP 集合通信，尤其是 MoE 中的 AllToAll 通信。第四是网络级精度，在关键场景下要使用 ns-3 获得分组级结果，而不是只使用简单的带宽公式。第五是调度级精度，要能够表达 PD 分离、KV 传输、资源竞争和请求到达过程。第六是校准精度，要使用真实或可信的 profile 和实验数据，量化仿真结果与基线之间的误差。

因此，我们的核心科研问题不是“如何增加一个 MoE 模块”，而是：

“如何构建一个同时覆盖请求调度、计算执行、集合通信与网络竞争的 LLM 推理仿真系统，并在可接受成本下获得可校准的高精度预测？”

我们当前可以进一步聚焦一个可验证的问题：

“在相同 token 总量和计算配置下，MoE 专家负载偏斜是否会通过 EP AllToAll 网络竞争，显著影响 TTFT、TPOT、吞吐和 P95/P99 尾部时延？引入更精细的通信和网络模型后，仿真结果与真实或可信基线之间的误差能下降多少？”

这个问题包含了两层含义。第一层是系统要能够模拟真实现象，包括请求到达、Prefill、Decode、MoE 算子、EP AllToAll、网络拥塞、资源竞争和 PD 调度。第二层是系统要能够被验证，我们必须量化不同建模层次对预测误差和运行成本的影响。

但这一周我们不直接回答完整科研问题。第一周的目标更基础，也更重要：建立全组一致、可复现、可追溯的基线，并确认系统各层当前能够模拟什么、不能模拟什么。

当前仓库可以理解为多个相互连接的层次。AICB 用于生成或描述工作负载；Vidur 从请求和调度视角模拟请求到达、Prefill、Decode、PD 分离以及请求级指标；Astra-Sim 负责执行工作负载和集合通信调度；SimCCL 把集合通信拆解为通信 flow；解析后端或 ns-3 负责计算网络时间，其中 ns-3 用于关键场景下的分组级网络仿真。最终，我们需要把通信和网络层的时延反馈到请求级模拟中，形成从请求到网络、再回到请求指标的闭环。

整体链路应逐步形成：

```text
请求到达与调度
      ↓
Prefill / Decode / MoE 算子与依赖
      ↓
TP / PP / EP 通信请求
      ↓
SimCCL / Astra-Sim 生成通信 flow
      ↓
解析模型或 ns-3 网络仿真
      ↓
通信时延回写请求级模拟
      ↓
TTFT、TPOT、吞吐、尾时延与误差评估
```

我们后续重点关注的是 MoE 的 EP AllToAll 通信。当前底层已经存在 AllToAll 相关能力，但“请求级动态 MoE 流量如何进入网络仿真、网络拥塞如何影响通信时延、通信时延如何反馈到 Vidur 的请求级结果”这条完整链路还没有建立。这条链路正是后续形成科研贡献的关键。

因此，MoE、PD 和 AllToAll 不是三个彼此独立的功能点。它们共同用于证明系统是否具备高精度预测能力。MoE 提供具有代表性的专家负载偏斜和 EP AllToAll 场景；PD 提供请求调度、Prefill/Decode 分离和 KV 传输场景；AllToAll 与 ns-3 提供通信竞争和网络拥塞场景。最终，我们要验证这些层次是否能够联动影响 TTFT、TPOT、吞吐和尾部时延，并通过真实或可信数据进行校准。

第一周统一使用仓库自带基线包。主工作负载使用 `example/workload_analytical.txt`，网络参数使用 `example/busbw.yaml`，最小通信冒烟使用 `example/microAllReduce.txt`，PD 调度验收使用 Vidur 的 `test_pd_separation.py`。

选择这套数据的原因是：它不依赖外部私有数据，所有人都能拿到；而且主工作负载中已经含有 AllToAll 和 `ALLTOALL_EP`，能直接覆盖未来研究的通信主线。需要强调的是，这只是第一周的固定、可控系统基线，不是最终科研实验数据集。后续我们还需要引入可控的 MoE 偏斜矩阵、真实或可信 profile，以及用于校准的实验数据。

在公开校准数据方面，我们选择 DeepSeek 的 `profile-data` 作为第一周就要解析的参考。成员四先输出 Prefill 和 Decode 的关键事件表，验证计算与 AllToAll 通信的顺序、等待关系和重叠比例；成员一、二、三以此约束后续任务图、通信接口和请求级回写设计。它不能替代端到端请求级测试，因此“仿真输出与 trace 的系统化对齐和误差分析”将在通信闭环实现后进行。AIOB 的真实画像需要 GPU，但第一周基线、公开 trace 解析、SimCCL、Vidur 和小规模 ns-3 不需要租用 GPU。只有在请求—通信—网络—指标闭环完成后，才按明确实验方案申请单机 GPU 或多节点 GPU/RDMA 资源。

本周结束时，我们不以代码量作为成功标准。成功标准是：四个人使用同一版本、同一输入、同一命令，得到可比较的结果；每个结果都能说明环境、版本、输入、命令、输出和问题；同时，我们能够明确当前系统在请求、计算、通信、网络和调度各层已经具备哪些能力，哪些链路尚未闭环。

更重要的是，后续每次新增能力都不能只报告“功能已经实现”。我们必须回答两个问题：它让系统多模拟了哪个真实现象？它让预测误差下降了多少，或者在哪些场景下使结果更可信？最终的实验结果应同时报告精度、运行成本和适用边界。


负责人负责项目架构、接口冻结、验收标准、仓库维护和结果汇总，重点推动请求级指标、计算级事件、通信 flow、网络仿真结果之间的接口设计，并建立误差评估框架。成员二负责通信与网络仿真基线，重点是 SimCCL、Astra-Sim、AllReduce、AllToAll、EP 通信以及解析模型和 ns-3 的边界。成员三负责 Vidur 与 PD 调度基线，重点是请求级指标、PD 配置、Prefill/Decode、KV 传输和预测器链路。成员四负责 AICB 工作负载、实验记录和文献整理，重点是工作负载字段、EP 通信数据、MoE 偏斜方案和校准数据设计。

协作上，我们遵守四条规则。

第一，不直接在主分支开发，所有改动通过 Issue、分支和 PR 合并。

第二，一个 PR 只解决一个问题，不混入无关格式化或重构。

第三，实验输出必须可追溯。任何性能结论都必须写明输入、环境、命令、随机种子、指标和误差计算方式。

第四，第一周发现的问题优先记录，不要为了让结果“看起来正确”而私自修改核心逻辑。当前不支持的能力必须明确写出边界，不能用主观判断替代实验验证。

本周每天进行一次简短同步。每个人只回答三件事：昨天完成了什么，今天准备做什么，当前阻塞是什么。周末复盘时，每人提交可复现实验记录和一页结果说明，并说明当前基线能够验证哪些能力、还缺少哪些闭环。

我们这一周先把基线站稳。基线稳定后，第二周开始实现固定 EP AllToAll 流量矩阵从 Vidur 到 SimAI 的端到端闭环；再往后逐步加入动态 MoE 偏斜、PD 场景下的 KV 传输、资源竞争和 ns-3 分组级网络仿真。每一步都要通过误差评估回答：新增建模是否让预测更接近真实或可信基线，以及为此付出了多少仿真成本。

最终，我们希望交付的不是若干孤立模块，而是一套能够在请求、算子、通信和网络多个层次联动预测性能，并量化精度、成本和适用边界的 LLM 推理仿真框架。
